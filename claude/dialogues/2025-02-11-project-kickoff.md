## awe9 の核心

このプロジェクトは, 単なるソフトウェア開発ではなく, **ソフトウェアそのものの存在意義を根本から問い直す**試みだと理解しました.

**出発点**: グローバル資本主義と西洋近代的制度が崩壊した 10 年後の世界. 技術水準は大幅に後退しているが, ゼロではない. この「空白状態」において, ソフトウェアはひとびとの生に有効かどうかすら問われている.

**想定する社会像**: 国家や大企業ではなく, 数十〜数百人の緩やかな集団とそのネットワーク. 加入・離脱が自由で, 顔の見える関係のなかで, 暴走を防ぐ仕組みを自律的に育てる社会. ここにアナキズムの思想が色濃く反映されていると感じます.

**重要な制約**: 巨大クラウド, HPC, 高速広域ネットワーク, 最新モバイルデバイスは前提としない. つまり, 現在のソフトウェア産業の基盤をほぼすべて取り払ったうえで, それでも意味のあるものを考える.

**特に印象的な点**:
- 「ソフトウェアはもう存在する余地がないのか」という問いが含まれていること. ソフトウェアの有用性自体が仮説であり, 結論ではない
- 「普通の文房具」が技術候補に入っていること. ソフトウェアに固執しない姿勢
- 対象分野の既存の区分 (エンタプライズ, 個人向け, エンタメ) も前提社会の変動のもとでは無効になりうるという認識
- ソフトウェアを提供する側もまた同様の集団を形作っているという, 提供者/利用者の境界を溶かす視点

深ソフトウェア工学との関係では, awe9 が具体的な実験と検証の場であり, 深ソフトウェア工学がその理論的枠組みを担う, という二重構造だと理解しています.

## Claude

私からのアクセスしやすさという観点で正直にお伝えします.

**最もアクセスしやすいもの:**

- **GitHub Issues / Projects** — `gh` コマンドで直接読み書きできます. Issue の作成・更新・コメントすべて可能です
- **リポジトリ内の Markdown ファイル** — 当然ながら最も自由に扱えます

**アクセスできないもの:**

- **Trello, Notion** — API アクセス手段がないので, 内容を見ることも更新することもできません

**私の意見としては:**

このプロジェクトの性質を考えると, **GitHub Projects** が適していると思います. 理由は:

- すでにリポジトリが GitHub にある
- 私が `gh` CLI で Issue の作成・参照・更新ができる
- プロジェクトが比較的シンプルなら, Issue をカード的に使う程度で十分
- 深ソフトウェア工学の探究と awe9 の開発を並行して追跡するのに, ラベルで区別できる

もうひとつの選択肢として, **artifacts/ 以下に Markdown で計画書を置く**というやり方もあります. これは最もシンプルで, 対話の中で直接編集でき, Git で変更履歴も残ります. ただし「進捗の可視化」は弱くなります.

両方を併用する手もあります — 大きな計画の構造は Markdown で, 個別のタスクや議論は GitHub Issues で.
